## 4. Concurrency (5 identical requests at once)

- Accept the same order x5: statuses `[200, 200, 400, 400, 400]` — **two succeeded** (check-then-write is not atomic)
- Verify the same magic link x5: `[200, 500, 500, 500, 500]` — one wins, the losers get **500**
- Five links for the same new email x5: `[200, 200, 200, 200, 500]` — one **500** (unique violation on Account.email)

## 5. Security

- **Any signed-in user can read any order's fulfillment (incl. the delivery message)**: `True` (the code has a comment saying it should check).
- 500 bodies include raw SQL text, parameters and the Postgres `cause` (constraint names, key values).
- GraphQL `limit` is unbounded (`limit: 100000` and `limit: -1` both return data).
- `/api/config` publicly returns `primeUiLicense`.
- WebSocket auth token travels in the query string.

## 6. Accepted input that probably should not be

- `price: "10"` (string) accepted and stored as `10`
- Order quantity `1_000_000_000` accepted: `{'price': 5000, 'quantity': 1000000000}`
- Unknown JSON fields silently ignored (`PATCH /users/me {"hacker":1}` -> 200)
- `PATCH` with `{}` -> 200 no-op; whitespace-only chat message -> 201
- Several PENDING orders for the same offer by the same user -> 201 each
- `DELETE /offers/:id` is a soft delete: afterwards `GET` still returns 200 with `status: ARCHIVED`, and it is still listed under the user

## 7. Test-suite findings

- 2 of 149 tests fail unless `MAGIC_LINK_BASE_URL` is set (verified: both pass with it). The unit test also hard-codes `http://192.168.0.50:4200`, so it only passes with that exact value.
- Auth e2e tests mount `authController` alone (no `/api` prefix, not the real `app`), so they never exercise the assembled app, CORS, plugin ordering or the routes' real paths.
- No e2e test asserts a domain error *body* (only the GraphQL test checks `errors` is absent); a handful assert a status. None cover the 500s above.
- Tests share one database with no per-test isolation; no fixed clock or fixed ids.
