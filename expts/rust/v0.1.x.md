```text

[ ] A person can create an offer.
[ ] A person can edit an offer.
```

## 1. Account and Authentication

### What is an account?

An account is a claim of identity on Haven. Specifically, it is a record that says: *this email address is controlled by someone, and they have interacted with Haven.*

An account is **not**:
- A profile (that is a participant concept, addressed separately)
- A permission set (that requires an authorization model)
- A user in the UI sense

An account is the authentication root. Sessions, offers, and every subsequent v0.1.x concept hangs from it.

In v0.1.x, the only identifier is an email address.

### What does sign-in actually require?

The full engineering journey beneath the checkbox:

```text
Person presents email address
    ↓
Normalize the email (lowercase, trim whitespace)
    ↓
Is this email already known?
    ├── No → create an Account record
    └── Yes → find the existing Account
    ↓
Generate a single-use credential (the magic link token)
    ↓
Persist the credential with an expiry
    ↓
Deliver the credential to the email address
    ↓
Person follows the link (presents the token)
    ↓
Validate the token: exists? not expired? not used?
    ↓
Consume the token (mark usedAt = now())
    ↓
Create a Session record
    ↓
Set a session cookie (HttpOnly, Secure, SameSite=Lax)
    ↓
Subsequent requests: read cookie → find session → verify not expired → attach Account to context
    ↓
Sign-out: invalidate the session record
```

### Engineering decisions: authentication

**Sign-up vs sign-in: should they be the same action?**

Investigation: if we have a separate sign-up form, a person must first register, then request a link, then verify — two round trips. If sign-up and sign-in are the same action (present your email, receive a link), the experience collapses to one interaction. The account is created on first use if it doesn't exist.

**Decision: sign-up and sign-in are the same action.** "Create an account" and "sign in" are one flow. Present email → receive link → follow link → you are in. If an account already exists for that email, no second account is created.

**Anti-enumeration: what do we tell someone who presents an email?**

Investigation: if we say "account not found," we've told an attacker which emails have accounts. If we always say "check your email," we've eliminated that information leak. The tradeoff is that a typo in your email gives no feedback — you wait for a link that never arrives.

**Decision: always respond with "check your email."** We do not distinguish between "account exists" and "account created." This is the correct behavior for a credential-based system.

**Credential type: magic link vs TOTP vs password**

Investigation:
- Password: requires hashing (bcrypt/argon2), requires forgot-password flow, increases attack surface (credential stuffing)
- TOTP (6-digit code): no email infrastructure, but loses the single-device-confirmation property, requires secure random generation
- Magic link: no password storage, no hashing, single-use token, expiry natural, consistent with the reference implementation

Magic link is the right choice. No passwords stored. No hashing infrastructure. Expiry is built into the design.

**Token delivery in dev: DOM injection vs file vs SMTP**

Three options investigated:

**Option A — DOM injection:** After sign-in POST in dev mode, render the magic link directly into the page HTML instead of (or alongside) sending an email. The person clicks it immediately in the browser.

Against ENGINEERING.md: "Everything must earn its existence." DOM injection adds a conditional rendering path that only exists in dev. Critically, it means the `mail!` template is **never called** — the email is never composed, the transport is never invoked. If the email template has a bug, we don't find it in dev. The dev code path does not exercise the production code path. This is the wrong abstraction.

Against ENGINEERING.md: "Don't trust magic. Understand the mechanism." We must test the real mechanism — email composition + transport dispatch — even in dev. DOM injection bypasses the mechanism entirely.

**Option B — Custom `MailSender` trait (original plan):** Write our own trait with a `LogSender` and a future `SmtpSender`. Now obsolete: Topcoat provides exactly this.

**Option C — `topcoat::mail` with `FileTransport`:** Topcoat has a first-party mail module (`topcoat = { features = ["mail"] }`). In dev, `FileTransport` writes each message as a `.eml` file to `target/mail/`. The email IS composed — the `mail!` macro runs, the `Transport` trait is invoked, the HTML body is rendered. The only difference from production is delivery destination (file vs SMTP). `MemoryTransport` is available for test verification.

**Decision: `topcoat::mail` with `FileTransport` for dev, `SmtpTransport` for production.** We do not build our own mail trait. We do not inject links into the DOM. The email composition and transport path are exercised in dev. To find the magic link during development: check `target/mail/` — the most recently written `.eml` file contains the full HTML email.

**Token representation: should plaintext and hashed tokens be different types?**

Investigation: in the reference implementation, the token stored in the DB is the same token sent in the link. This means: if the database is compromised, an attacker has working magic link tokens. Better: store a hash of the token. The link contains the plaintext token. The server hashes on verification and compares.

**Decision: store `SHA-256(token)` in the database. The link contains the raw token. The Rust type system enforces this: `PlaintextToken` and `HashedToken` are distinct newtypes. A function that takes `HashedToken` cannot accidentally receive a `PlaintextToken`.** The compiler makes this class of bug impossible.

**Token expiry: what is a reasonable lifetime?**

Investigation: too short → frustrating (person reads email too slowly). Too long → credential lives longer than necessary. 15 minutes is the common convention for magic links.

**Decision: 15 minutes.** After expiry, the token is rejected and the person must request a new link.

**Session lifetime: how long does a session last?**

Investigation: 30 days is what `topcoat_session` defaults to and what the reference uses. This is reasonable for "keep me signed in" behavior.

**Decision: 30 days.** The session record is stored in the database. The cookie has a matching `Max-Age`.

**Session token storage: should session tokens be hashed in the database?**

Investigation: `topcoat_session` documentation says it stores token hashes. This is the same property as the magic link: if the session table is compromised, the attacker does not get working session cookies. The plaintext token lives only in the cookie.

**Decision: session tokens are hashed in the database.** `topcoat_session` handles this if we configure it correctly. Same newtype discipline applies.

**What does a Session record need to contain?**

```
id          UUID        primary key
account_id  UUID        foreign key → Account.id, on delete cascade
token_hash  text        SHA-256 of the session token
expires_at  timestamptz when the session expires
created_at  timestamptz when the session was established
ip_address  text        (nullable) for observability, not enforcement
user_agent  text        (nullable) for observability, not enforcement
```

`ip_address` and `user_agent` are stored for observability (can I see which devices have sessions?) but not enforced (we don't invalidate a session if the IP changes — this breaks legitimate mobile users).

## 2. Account and User — two different things

### The distinction

Account and User are not the same concept. They must not be conflated.

**Account = authentication (authn).** It is proof of identity. It says: "someone controls this email address." It issues sessions, holds credentials, handles verification. It has no knowledge of Haven as a platform. It does not know what an offer is.

**User = platform participant (authz + platform context).** It is the thing that owns offers, is the subject of authorization, and will carry platform-specific identity (username, profile). It is "a person on Haven" — not "a person who authenticated."

This is a principled boundary, not a future-proofing concern. It is correct now.

### Why the offer must belong to User, not Account

An offer belongs to a platform participant, not to an authentication mechanism.

If `offer.account_id` were the FK: the offer belongs to an email address. That is semantically wrong. The offer belongs to *the person on Haven*. Their email may change (account recovery, email update). Their authentication method may change (OAuth added later). The offer must survive both. The FK targets the platform identity, not the auth identity.

There is also a compiler argument: if offers had `account_id`, nothing would prevent a handler from passing an `AccountId` into an authorization check that should be checking platform ownership. With `user_id` as the FK, passing an `AccountId` there **does not compile**. The types enforce the boundary.

### What User contains in v0.1.x

In v0.1.x, User is thin. No username. No bio. No avatar. Those fields belong to future versions when the concept becomes visible to others.

What User has:
```
id          UUID    primary key
account_id  UUID    FK → account.id (1:1)
created_at  TIMESTAMPTZ
updated_at  TIMESTAMPTZ
```

The 1:1 relationship to Account is intentional. One authentication identity = one platform participant. The separation enforces that authentication concerns stay in Account and platform concerns stay in User.

### User creation

User is created automatically on first sign-in, immediately after the session is established. There is no onboarding step visible to the person — from their perspective, they followed a link and they are in. Internally, the system has created an Account and a User.

If the Account already exists (returning sign-in), the User already exists too. No second User is created.

### The database after this decision

```
Account   — authn: email, verification, sessions
User      — platform: the Haven participant, owner of offers
Session   — links to Account
MagicLink — links to Account (used to verify email)
Offer     — links to User
```

## 3. The Offer

### What is an offer?

An offer is something a person is willing to provide. In v0.1.x, only the person who created it can see and manage it. It needs to be:
- Identifiable: the person can return to it
- Owned: the person who created it is the only one who can modify it
- Describable: enough information to capture what the person intends to offer
- Manageable: can be edited and deleted

### What fields genuinely exist in v0.1.x?

**`id`**: UUID, generated on creation. Necessary — this is how we navigate to a specific offer.
**Decision: YES.**

**`user_id`**: FK to User. This is ownership. The offer belongs to exactly one platform participant, not to an authentication identity.
**Decision: YES.**

**`title`**: The name of the offer. Required. This is the minimum meaningful description of what is being offered. Without a title, the offer has no identity.
**Decision: YES. Required. 1–255 characters. Whitespace-only is rejected.**

**`description`**: Free text. Optional. More detail than the title.
**Decision: YES. Optional. No hard length limit at the DB level — the UI can suggest a practical limit.**

**`price`**: An integer in minor currency units (pence, cents, etc.). Does price have any behavior in v0.1.x?

Investigation: the offer is not visible to others. No transaction happens. Does the person need to record a price at creation time? A person creating an offer likely has a price in mind. Capturing it at creation is reasonable. It is not just a future-version concern — it is part of describing the offer.

But: if price is optional and defaults to 0, does that represent "free" or "unset"? These are different states. A free offer (price = 0) is a valid concept. An unset price is also valid — the person may not have decided yet.

For v0.1.x, with no transactions and no visibility: the distinction between "free" and "unpriced" is not observable. Either way, the offer exists and the person can manage it.

**Decision: price is optional. If not provided, it is null (not zero). Zero means "free." Null means "not set."** This avoids conflating two states that are semantically different, even if the difference isn't observable yet.

**`currency`**: ISO 4217 code. Required when price > 0. Meaningless when price = null or price = 0.

**Decision: currency is nullable. If price > 0, currency is required. If price is null or 0, currency may be null.** This is a domain invariant: an offer with a non-zero price and no currency is invalid.

**`offer_type`** (PRODUCT / SERVICE / APPOINTMENT):

Investigation: does any behavior in v0.1.x branch on offer type? Validation rules? DB queries? UI rendering? Authorization?

In v0.1.x: no. The type is a label. The person categorizes their offer, but no system behavior differs based on that category. Nobody can see the offer, so the category serves no discovery purpose. There is no scheduling system for APPOINTMENT.

Counter-argument: "the person wants to categorize their offer at creation time." Perhaps. But the question is whether the *system* needs to know the type, not whether the *person* finds it useful. The person's categorization impulse can be captured in the title or description for now.

The real test: **what breaks if we remove offer_type from v0.1.x?** Answer: nothing. No behavior changes. No invariant is violated.

**Decision: offer_type does not exist in v0.1.x.** It will be introduced when a version requires behavior that depends on it.

**`status`** (ACTIVE / PAUSED / ARCHIVED):

Investigation: what would status mean in v0.1.x?
- ACTIVE: visible. But visible to whom? Nobody can see offers in v0.1.x.
- PAUSED: hidden. Hidden from whom?
- ARCHIVED: soft-deleted. Preserved but inaccessible.

Does v0.1.x need a status machine? The operations are: create, edit, delete. Delete removes the offer from the database. There is no "pause" operation in the requirements. There is no "archive" operation.

The only reason to have status in v0.1.x would be if delete were a soft delete (marking status = ARCHIVED rather than removing the row). But soft delete requires a reason: preventing broken links, audit history, recovery. In v0.1.x, nobody has a link to someone else's offer (visibility is v0.2.x), so there are no links to break. Audit history is not a requirement. Recovery is not a requirement.

**What breaks if we remove status from v0.1.x?** Nothing. An offer exists or it doesn't.

**Decision: status does not exist in v0.1.x. Delete is a hard delete.** When visibility introduces the concept of "an offer another person has seen," soft deletion may become relevant. That version will introduce the status concept.

**`images`**: URLs to images.

Investigation: images require a source. Either:
- The person uploads images → requires file storage (S3, local, etc.)
- The person provides URLs → requires accepting arbitrary URLs (XSS risk, dead links, etc.)

In v0.1.x, the offer is not visible to others. Images serve no purpose that a title and description don't already serve at this stage. The infrastructure cost is real. The benefit is invisible (literally).

**Decision: images do not exist in v0.1.x.**

**`created_at`**: Set once on creation. Needed for "when was this created?"
**Decision: YES.**

**`updated_at`**: Updated on every edit. Needed for "when was this last changed?"
**Decision: YES.**

### The Offer — final schema

```sql
CREATE TABLE offer (
    id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id     UUID NOT NULL REFERENCES "user"(id) ON DELETE CASCADE,
    title       VARCHAR(255) NOT NULL CHECK (length(trim(title)) > 0),
    description TEXT,
    price       INTEGER CHECK (price IS NULL OR price >= 0),
    currency    CHAR(3),
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT currency_required_when_priced
        CHECK (price IS NULL OR price = 0 OR currency IS NOT NULL)
);
```

The `currency_required_when_priced` constraint enforces the domain invariant **at the database level**, not just the application level. A bug in the application cannot create an inconsistent record.

### Offer invariants

| Invariant | Enforcement |
|---|---|
| Title is not empty or blank | DB CHECK constraint + application validation |
| Price is non-negative | DB CHECK constraint |
| Currency is required when price > 0 | DB CHECK constraint |
| Offer belongs to exactly one User (platform participant) | FK to `user.id`, NOT NULL |
| Only the owner can edit or delete | Application-level, checked in handler |
| `created_at` is immutable | Application-level (UPDATE never touches it) |
| `updated_at` reflects latest change | Application-level (set in every UPDATE) |

## 4. Create, Edit, Delete

### Create

**Who can create?** Only an authenticated person (valid session). No session → redirect to sign-in.

**Input:**
```
title       required, string, 1–255 chars, non-blank after trim
description optional, string
price       optional, non-negative integer
currency    optional, CHAR(3) — required if price > 0
```

**Process:**
1. Validate input (Rust struct + validation methods)
2. Generate UUID
3. Set `account_id` from the session
4. Set `created_at` and `updated_at` to now()
5. INSERT into `offer`
6. On success: redirect to the offer's page
7. On validation failure: re-render the form with errors

**After creation, where does the person go?**

This is a real v0.1.x question. There is no offer listing. The person just created an offer — now what?

Option A: Redirect to `/offers/{id}` (the offer's own page with edit/delete links)
Option B: Redirect to `/offers/new` with a success message and a link to the created offer
Option C: Redirect to some dashboard that lists the person's offers

Option C is off-limits (that requires an offer listing, which is arguably v0.2.x territory). But: managing offers (edit/delete) requires navigating to them. The offer's own page is the minimal navigation surface.

**Decision: after creation, redirect to `/offers/{id}`.** This page shows the offer details with links to edit and delete. It is not a "browse" page — it is the management surface for one specific offer. The person can access it via the URL they're redirected to.

### Edit

**Who can edit?** Only the offer's owner. Anyone else → 403.

**Editable fields:**
```
title       same rules as create
description same as create
price       same as create
currency    same as create
```

**Immutable fields:**
```
id          set at creation
user_id     set at creation (owner never changes)
created_at  set at creation
```

**Process:**
1. Authenticated (session required)
2. Load offer by ID — if not found: 404
3. Verify `offer.account_id == session.account_id` — if not: 403
4. Validate input
5. UPDATE offer (set new values + `updated_at = now()`)
6. On success: redirect to `/offers/{id}`
7. On validation failure: re-render edit form with errors

**What happens if validation fails mid-edit?**

The original values should be preserved as defaults. The person sees what they had, with error messages indicating what's wrong.

### Delete

**Who can delete?** Only the offer's owner.

**Process:**
1. Authenticated (session required)
2. Load offer by ID — if not found: 404
3. Verify `offer.account_id == session.account_id` — if not: 403
4. DELETE offer (hard delete)
5. On success: redirect to `/` (or a confirmation page — no offer listing exists)

**Hard delete or soft delete?**

Investigation: soft delete (marking a row as deleted rather than removing it) is useful when:
- Other people may have bookmarked the offer URL (broken link prevention)
- Audit history is required
- The delete must be reversible

In v0.1.x, nobody can see the offer except the owner. There are no external bookmarks. Audit history is not a requirement. Reversibility is not a stated requirement.

**Decision: hard delete.** The row is removed. The UUID is freed.

**What is the DELETE endpoint?**

HTML forms do not support the HTTP DELETE method. Standard practice for forms: `POST /offers/{id}/delete`. The handler performs authorization and deletion.

## 5. Authorization boundary

This is worth stating explicitly because it applies to every operation.

The authorization model for v0.1.x is simple: **an account can only modify its own offers.** There are no roles, no admin accounts, no delegation.

The authorization check must happen **after authentication and after loading the resource**, in that order:

```text
Is the person signed in? → No → redirect to sign-in
Does the offer exist?    → No → 404
Does the person own it?  → No → 403
Proceed with operation
```

The reason order matters: if we return 404 for "doesn't exist" and 403 for "not owner," we reveal that the offer exists (enumeration). For v0.1.x, this is an acceptable tradeoff — we're not protecting a large user base. But it's worth noting.

A stricter approach: always return 404 (never reveal whether a resource exists to non-owners). This is the correct behavior for a real system.

**Decision: return 404 when the offer doesn't exist AND when the person is not the owner.** An attacker cannot distinguish "offer doesn't exist" from "offer exists but isn't yours." This is the correct behavior.

## 6. Persistence

### The question

What database does the experiment use?

### Investigation

**SQLite:**

Pros: zero infrastructure (no Docker container), single file, SQLx compile-time queries work.

Cons:
- Arrays don't exist in SQLite — the `text[]` type from the reference requires JSON in SQLite
- UUID functions differ
- Transaction semantics differ in edge cases
- Concurrent write behavior differs fundamentally (WAL mode vs MVCC)
- Testing a SQLite schema does not validate a Postgres schema
- The reference uses Postgres — the experiment should use the same engine to compare meaningfully

**Same Postgres, shared tables with prefix:**

Pros: same instance, easy access.

Cons: the experiment schema lives alongside the TS schema — messy, potential for accidental cross-contamination, harder to isolate.

**Separate Postgres database (`haven_rust`):**

Pros: same engine, same Postgres instance (already running in Docker), fully isolated, own migrations, own schema, can be blown away and recreated without affecting the TS Haven data.

Cons: requires creating the database once.

**Decision: separate Postgres database named `haven_rust`.** Same Docker Compose postgres service, new database. SQLx compile-time queries target `haven_rust`. Migrations are in `expts/rust/migrations/`.

### Schema decisions

The schema is defined by the investigation above:

```sql
-- Account: authentication identity (authn only)
CREATE TABLE account (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    email           TEXT NOT NULL UNIQUE,
    email_verified  BOOLEAN NOT NULL DEFAULT false,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- User: platform participant (authz + platform context)
-- Thin in v0.1.x — no profile fields yet. Auto-created on first sign-in.
CREATE TABLE "user" (
    id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    account_id  UUID NOT NULL UNIQUE REFERENCES account(id) ON DELETE CASCADE,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- MagicLink: single-use credential for email verification (links to Account)
CREATE TABLE magic_link (
    id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    email       TEXT NOT NULL,
    token_hash  TEXT NOT NULL UNIQUE,
    expires_at  TIMESTAMPTZ NOT NULL,
    used_at     TIMESTAMPTZ,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- Session: authenticated session (links to Account)
CREATE TABLE session (
    id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    account_id  UUID NOT NULL REFERENCES account(id) ON DELETE CASCADE,
    token_hash  TEXT NOT NULL UNIQUE,
    expires_at  TIMESTAMPTZ NOT NULL,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    ip_address  TEXT,
    user_agent  TEXT
);

-- Offer: something a platform participant is willing to provide (links to User)
CREATE TABLE offer (
    id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id     UUID NOT NULL REFERENCES "user"(id) ON DELETE CASCADE,
    title       VARCHAR(255) NOT NULL CHECK (length(trim(title)) > 0),
    description TEXT,
    price       INTEGER CHECK (price IS NULL OR price >= 0),
    currency    CHAR(3),
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT currency_required_when_priced
        CHECK (price IS NULL OR price = 0 OR currency IS NOT NULL)
);
```

**snake_case vs camelCase column names:**

The reference uses camelCase (Drizzle ORM convention). PostgreSQL is case-insensitive by default and normalizes to lowercase unless quoted. Using snake_case natively avoids quoted identifiers.

**Decision: snake_case column names throughout.** This is idiomatic for Postgres and maps naturally to Rust's field naming convention via SQLx.

## 7. Crate structure

### The principle

Modules are conventions. Crates are contracts.

A module boundary says: "please don't reach across this line."
A crate boundary says: "you cannot reach across this line — the compiler will not allow it."

Clean architecture requires that no layer bleeds into another. That guarantee cannot be provided by a module. It requires a crate. The domain layer must be physically incapable of importing a database driver. The database layer must be physically incapable of importing Topcoat. These are not style rules — they are compiler-enforced invariants about the code itself.

### The workspace

```
expts/rust/
├── Cargo.toml                   # workspace root
└── crates/
    ├── haven-domain/            # innermost layer: types, rules, validation — zero I/O
    ├── haven-db/                # persistence layer: SQLx queries, migrations
    └── haven-web/               # presentation layer: Topcoat pages, handlers, session
```

### Layer boundaries (compiler-enforced)

```text
haven-domain
    ↑         (depends on)
haven-db
    ↑         (depends on)
haven-web
    ↑         (depends on)
haven-domain
```

Dependency direction is strictly inward. No layer may import from a layer above it.

| Layer | May import | May NOT import |
|---|---|---|
| `haven-domain` | `uuid`, `thiserror`, `serde` (derive only) | `sqlx`, `tokio`, `topcoat`, `axum` — anything with I/O |
| `haven-db` | `haven-domain`, `sqlx`, `tokio`, `uuid` | `topcoat`, `axum` |
| `haven-web` | `haven-domain`, `haven-db`, `topcoat`, `tokio` | raw SQL strings, domain logic |

These constraints are not documented agreements. They are enforced by each crate's `Cargo.toml`. If `haven-domain` does not list `sqlx` as a dependency, it is physically impossible to use SQLx there. The build fails.

### haven-domain — what lives here

Pure types and domain rules. No I/O of any kind. No async. This crate compiles to a library with zero runtime dependencies.

```
crates/haven-domain/src/
├── lib.rs
├── account.rs       # Account, AccountId, Email
├── session.rs       # Session, SessionId, PlaintextToken, HashedToken
├── magic_link.rs    # MagicLink, VerificationToken
└── offer.rs         # Offer, OfferId, CreateOffer, UpdateOffer, Price, CurrencyCode
```

Nothing in this crate performs a database query, sends an HTTP request, reads a file, or performs any action with a side effect. The compiler proves this because none of those capabilities are in its dependency tree.

### haven-db — what lives here

All database interaction. SQLx queries against the `haven_rust` Postgres database. Migrations. No HTTP, no Topcoat, no session handling.

```
crates/haven-db/src/
├── lib.rs
├── accounts.rs      # find_by_email, create, mark_verified
├── sessions.rs      # create, find_by_token_hash, delete
├── magic_links.rs   # create, find_by_token_hash, consume
└── offers.rs        # create, find_by_id, find_by_account, update, delete
```

Functions in this crate take and return `haven-domain` types. The interface between layers is expressed entirely in domain types. A caller in `haven-web` never sees a raw SQL row — it receives an `Offer`, an `Account`, a `Session`.

### haven-web — what lives here

Topcoat pages, Axum handlers, session middleware integration. No domain logic, no raw SQL. Mail is handled entirely by `topcoat::mail` — no custom mail abstraction needed here.

```
crates/haven-web/src/
├── main.rs
├── app.rs                   # root layout
└── app/
    ├── auth/
    │   ├── sign_in.rs       # GET /auth/sign-in, POST /auth/sign-in
    │   └── verify.rs        # GET /auth/verify?token=...
    └── offers/
        ├── new.rs           # GET /offers/new, POST /offers/new
        ├── id.rs            # GET /offers/{id}
        └── id/
            ├── edit.rs      # GET /offers/{id}/edit, POST /offers/{id}/edit
            └── delete.rs    # POST /offers/{id}/delete
```

### What the crate boundary catches

| Mistake | What prevents it |
|---|---|
| Domain logic calling the database directly | `haven-domain` has no `sqlx` dependency — won't compile |
| A page handler embedding raw SQL | `haven-web` has no `sqlx` dependency — won't compile |
| DB layer importing Topcoat types | `haven-db` has no `topcoat` dependency — won't compile |
| Domain layer growing async side effects | No `tokio` in `haven-domain` — won't compile |

## 8. Rust type decisions

### Newtypes — what earns a newtype?

A newtype is justified when two values of the same underlying type can be confused — where the compiler should prevent passing one where the other is expected.

| Type | Underlying | Justification |
|---|---|---|
| `AccountId` | `Uuid` | Cannot be confused with `OfferId` or `SessionId` |
| `OfferId` | `Uuid` | Cannot be confused with `AccountId` |
| `SessionId` | `Uuid` | Cannot be confused with `AccountId` |
| `Email` | `String` | Guarantees the string is a valid email format |
| `PlaintextToken` | `String` | Cannot be stored where `HashedToken` is expected |
| `HashedToken` | `String` | Cannot be sent to a user where `PlaintextToken` is expected |
| `Price` | `i32` | Enforces non-negative invariant at construction |
| `CurrencyCode` | `String` | Enforces 3-char ISO 4217 format |

`Email` is constructed via `Email::parse(raw: &str) -> Result<Email>`. After construction, it is guaranteed valid. Any function that takes an `Email` receives a validated email — no re-validation needed.

`PlaintextToken` and `HashedToken` prevent the class of bug where a raw token is stored in the DB, or a hash is sent to the user. The types make this **physically impossible** rather than a code review concern.

### What does a session-authenticated handler look like?

Rather than checking the session cookie in every handler, the session context should be extracted once and passed as a typed value. An authenticated handler receives `SessionContext { account_id: AccountId, ... }` as a parameter. An unauthenticated request cannot reach a handler that requires `SessionContext`.

This is what Topcoat's `Cx` (context) and `topcoat_session` enable: the session state is part of the request context, accessible in any page or handler.

## 9. Topcoat integration for v0.1.x

### Cargo features required

```toml
# crates/haven-web/Cargo.toml
[dependencies]
topcoat = { version = "0.9.0", features = ["mail", "session", "router"] }
```

In dev (via environment config):
```toml
topcoat-mail = { version = "0.9.0" }  # FileTransport
```

In production:
```toml
topcoat = { version = "0.9.0", features = ["mail", "mail-smtp", "session", "router"] }
```

### What Topcoat gives us for these specific requirements

| Requirement | Topcoat mechanism |
|---|---|
| Sign-in page | `#[page]` returning HTML form |
| Sign-in POST | Axum route handler (POST form → process → redirect) |
| Magic link email | `mail!` macro + `send(cx, mail)` → `FileTransport` (dev) / `SmtpTransport` (prod) |
| Verify link | `#[page]` reading `token` query param |
| Create offer | `#[page]` (GET, auth guard) + Axum POST handler |
| Edit offer | `#[page]` (GET, auth guard, load offer) + Axum POST handler |
| Delete offer | Axum POST handler (no GET — form-based) |
| Session cookie | `topcoat::session` — integrated with Topcoat's `Cx` |
| Test email capture | `MemoryTransport` — clones share captured messages |

### What we do NOT use in v0.1.x

- `#[shard]`: no reactive fragments needed — all interactions are form-based with full-page navigation
- `signal(cx, \|\| value)`: no client-side state — the UI is purely server-rendered
- `topcoat-datastar`: no SSE needed
- `topcoat-ui`: using Tailwind directly for styling (the component library assumes shadcn conventions we haven't adopted)

### The client/server boundary in this version

Every interaction in v0.1.x follows the same pattern:

```text
Browser GET → Topcoat #[page] renders HTML form
Browser POST → Axum handler processes form data → redirect
Browser follows redirect → next page
```

This is classic POST/Redirect/GET. No JavaScript required for any core functionality. The Rust type system enforces correctness at the handler level, not across a wire protocol.

## 10. Frontend

### The rule

Frontend and backend are implemented in sync. When a backend handler is written, its corresponding page is written in the same unit of work. A handler with no rendered page is not done. A page with no handler behind it is not done. Neither exists without the other.

### Styling

`topcoat = { features = ["tailwind"] }` + Tailwind CSS. The root layout includes the Tailwind stylesheet. Components use Tailwind utility classes. No external component library dependency — Topcoat UI copies components into the project, which adds more surface area than v0.1.x needs. We write our own minimal components.

### The email template

The magic link email is declared with the `mail!` macro and rendered as HTML by Topcoat's view engine. It shares the same `view!` vocabulary as the pages.

```rust
let message = mail! {
    from: ("Haven", "no-reply@haven.local"),
    to: email.as_str(),
    subject: "Sign in to Haven",
    html: {
        <h1>"Sign in to Haven"</h1>
        <p>"Follow this link to sign in. It expires in 15 minutes."</p>
        <a href=(verify_url)>"Sign in"</a>
        <p>"If you didn't request this, you can ignore it."</p>
    },
}?;
send(cx, message).await?;
```

This template is exercised on every sign-in in dev (FileTransport writes it to `target/mail/`). It is not mocked. It is not injected into the DOM.

### Pages

#### Sign-in (`GET /auth/sign-in`)

```
What the person sees:
  - Haven wordmark
  - Heading: "Sign in"
  - Email input field (required, type=email)
  - Submit button: "Send link"
  - No password field
  - No "create account" link (sign-up and sign-in are the same action)

What happens on POST:
  - Normalize and validate email
  - Create or retrieve Account
  - Create or retrieve User (auto, linked to Account)
  - Generate PlaintextToken
  - Store SHA-256(token) in magic_link table with expiry
  - Send email via topcoat::mail
  - Redirect to GET /auth/sent

Error states:
  - Invalid email format → re-render form with inline error
  - Server error → re-render form with generic error (no details leaked)
```

#### Sent confirmation (`GET /auth/sent`)

```
What the person sees:
  - Heading: "Check your email"
  - Message: "We sent a link to [email]. It expires in 15 minutes."
  - Note: "Didn't get it? Check your spam folder."
  - No resend link in v0.1.x (out of scope)

Note: identical response whether the account is new or existing (no enumeration).
```

#### Verify (`GET /auth/verify?token=...`)

```
What the person sees:
  - Brief loading state: "Signing you in..."
  - On success: redirect to GET /offers/new
  - On failure (expired/used/not found): error page
    - Heading: "Link expired or invalid"
    - Message: "This sign-in link has expired or already been used."
    - Action: link to GET /auth/sign-in

What happens:
  1. Read token from query string
  2. Hash it: SHA-256(token)
  3. Look up magic_link by token_hash
  4. Validate: exists? not expired? not used?
  5. Mark magic_link.used_at = now()
  6. Create session record (token_hash in DB, plaintext in cookie)
  7. Set session cookie (HttpOnly, Secure, SameSite=Lax)
  8. Redirect to /offers/new
```

#### Create offer (`GET /offers/new` + `POST /offers/new`)

```
What the person sees:
  - Heading: "New offer"
  - Title field (required, text input, max 255 chars)
  - Description field (optional, textarea)
  - Price field (optional, number input, min 0)
  - Currency field (optional, 3-char text, shown/required when price > 0)
  - Submit button: "Create offer"

Auth: if no session → redirect to /auth/sign-in

Validation errors shown inline next to each field.
On success → redirect to GET /offers/{id}
```

#### Offer detail (`GET /offers/{id}`)

```
What the person sees:
  - Title (heading)
  - Description (if set)
  - Price and currency (if set), formatted (e.g. "£10.00") or "Free" (price=0)
  - Created and last updated timestamps
  - "Edit" button → GET /offers/{id}/edit
  - "Delete" button → form POST to /offers/{id}/delete (with confirmation)

Auth + ownership:
  - No session → redirect to /auth/sign-in
  - Non-owner or not found → 404 page
```

#### Edit offer (`GET /offers/{id}/edit` + `POST /offers/{id}/edit`)

```
What the person sees:
  - Heading: "Edit offer"
  - Same fields as create, pre-filled with current values
  - Submit button: "Save changes"
  - Cancel link → GET /offers/{id}

Auth + ownership:
  - No session → redirect to /auth/sign-in
  - Non-owner or not found → 404 page

On success → redirect to GET /offers/{id}
On validation error → re-render with errors, preserving user's input
```

#### Delete (`POST /offers/{id}/delete`)

```
No GET page. The delete button on the offer detail page is a form with method=POST.
A confirmation step is added: the submit button requires a second click
(or a JavaScript-free confirmation via a dedicated /offers/{id}/delete
confirmation page if needed — TBD during implementation).

Auth + ownership:
  - No session → redirect to /auth/sign-in
  - Non-owner or not found → 404

On success → redirect to / with a flash message: "Offer deleted."
```

#### Root (`GET /`)

```
Authenticated: redirect to /offers/new
  (no offer listing in v0.1.x — /offers/new is the entry point)

Unauthenticated: redirect to /auth/sign-in
```

### The root layout

Every page is wrapped in a root HTML document layout:
- `<!DOCTYPE html>`, `<html lang="en">`, `<head>` with charset, viewport, title
- Tailwind stylesheet link
- A minimal nav: Haven wordmark
- A main content area where pages render
- Flash message area (session-based: one-time messages after redirects)

## 11. Verification

**v0.1.x is done when:**

### Functional

1. A person can submit their email address and receive a magic link (`.eml` file written to `target/mail/` in dev)
2. The email HTML template is correct and readable
3. Following the link creates a session
4. An invalid or expired token is rejected with an error page
5. The same token cannot be used twice
6. A person with a valid session can create an offer with a title
7. A person can provide optional description, price, and currency
8. A person cannot create an offer with a blank title
9. A person cannot set price > 0 without a currency
10. A person can edit their offer and see the changes reflected
11. A person can delete their offer and it is gone
12. A person without a session is redirected to sign-in on protected pages
13. A person cannot edit or delete another person's offer (receives 404)
14. Every page renders correctly in a browser (not just curl)
15. Validation error messages appear inline next to the failing field

### Type guarantees (compile-time)

1. `cargo build` succeeds with `RUSTFLAGS="-D warnings"`
2. An `AccountId` cannot be used where `OfferId` is expected — the code does not compile
3. A `UserId` cannot be used where `AccountId` is expected — the code does not compile
4. A `PlaintextToken` cannot be stored where `HashedToken` is expected — the code does not compile
5. Adding a new field to the `Offer` struct surfaces every non-exhaustive pattern match
6. SQLx `query!` macros are verified against the actual schema — a schema change breaks the build
7. `haven-domain` has zero I/O dependencies — `cargo check -p haven-domain` passes with no `sqlx`, `tokio`, or `topcoat` in its dependency tree

### Database guarantees

1. A blank title cannot be inserted (DB CHECK constraint)
2. A price > 0 without a currency cannot be inserted (DB CHECK constraint)
3. Deleting an Account cascades to its User, Sessions, and Offers
4. A magic link token is stored as a hash — the plaintext never touches the database

### Performance (load testing)

The load-testing gate criterion for v0.1.x is to be confirmed — it should match or exceed the gate established for the TS implementation for equivalent operations.

| Soft delete | Nothing protects external links to offers; hard delete is correct |
