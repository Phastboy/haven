# v0.7 local query-plan evidence — 2026-10-28

PostgreSQL client 18.6; local `haven_rust`, not deployed inventory. No persistent
rows, indexes or statistics were changed. Fixture tables and indexes were TEMP,
ANALYZE targeted TEMP tables, and the transaction ended with ROLLBACK.

## Inventory

120,196 offers, all visible (`image_count >= 1`); 120,190 titles match
`Test Offer [number] from User [number]`. The other six are Feed Offer 1–5 and
New Title. Zero messages; one saved row. `haven_load_test` has 4,280 offers,
zero messages and zero saves. This inventory cannot ground topic categories or
represent real personal histories. The category column is not implemented.

## Existing public/saved queries

A public 21-row projection used `idx_offer_feed_visible`: execution 0.689 ms,
18 shared buffer hits / 3 reads. The one-row saved query used a bitmap scan on
`idx_saved_offer_user_created`, primary-key offer lookup and a small sort:
1.324 ms. These are single observations, not throughput or dense-save evidence.

## Temporary inquiry experiment

[SQL](V0.7_QUERY_PLANS.sql) clones the local offers into a TEMP table with the
relevant ID and visible-feed indexes. It creates 30,000 messages for a dense
sender (10,000 offers, three messages each), five for a sparse sender, and matching
participant conversations. Baseline uses the existing offer/time message index;
indexed runs add `(sender_id, offer_id, created_at DESC) WHERE offer_id IS NOT NULL`.

[Raw EXPLAIN (ANALYZE, BUFFERS) output](V0.7_QUERY_PLANS.txt) follows this order:

| Run | History | Shape/order | Execution ms |
|---|---|---|---:|
| Baseline | Dense | EXISTS / offer age | 2.950 |
| Baseline | Dense | Aggregate / last inquiry | 123.821 |
| Baseline | Sparse | EXISTS / offer age | 68.098 |
| Baseline | Sparse | Aggregate / last inquiry | 4.172 |
| Sender index | Dense | EXISTS / offer age | 1.755 |
| Sender index | Dense | Aggregate / last inquiry | 154.472 |
| Sender index | Sparse | EXISTS / offer age | 63.275 |
| Sender index | Sparse | Aggregate / last inquiry | 0.260 |
| Sender index | Dense | Single offer join aggregate / last inquiry | 155.185 |
| Sender index | Sparse | Single offer join aggregate / last inquiry | 0.335 |

Dense EXISTS drives from the ordered offer index and probes messages 191 times
to find 21 results. Sparse EXISTS becomes a hash semi join and scans all 120,196
offers, despite the sender index selecting only five messages. Sender-first
aggregation avoids that full offer scan for sparse history. Dense aggregation
reads 30,000 messages, groups 10,000 offers and sorts the result; the two-offer-join
shape also performs 10,000 final offer lookups. Its estimated aggregate cardinality
is only 10 versus 10,000 actual rows, a material estimation error around participant
join conditions. The single-offer-join alternative still scans all offers in its
dense hash join and does not improve this observation. Observed sorts stayed in
memory (no spill); dense final top-N sort used 29 kB.

## Recommendation and limits

Keep activity ordering as the retrieval decision and sender-first aggregation as
the initial query shape to validate. The sender index helps sparse selection;
it is not a dense-history performance solution. Before implementation acceptance,
measure alternate participant-pair expressions and deduplication before owner
validation, retaining all authorization checks, and recheck estimates and buffers.
Do not add persistent summary tables merely from this experiment. Before building
Inquired, spike the best read-time query on dense histories under the contract's
load. If it misses the budget, maintain per-person/per-offer last-inquiry rows on
qualifying message writes and backfill existing history. Record the result and
chosen design first. The typed title/price step does not run this load spike.

These single executions have uncontrolled cache effects, TEMP local buffers,
synthetic conversation distribution, no concurrent load and reduced row projections.
They compare different product orderings, not interchangeable optimizations.
They do not establish a 1,000 RPS gate. Category/price/title selectivity, later-page
keysets, empty histories, unrelated senders, dense saves, owner replies and invalid
participant tags still require the full fixture matrix. Category-index EXPLAIN
awaits the actual category migration; no category access-path claim is made.

Reproduce from the Rust workspace with:

```sh
psql -X -v ON_ERROR_STOP=1 -d haven_rust -f V0.7_QUERY_PLANS.sql
```
