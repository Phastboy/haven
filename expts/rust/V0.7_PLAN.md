## Scope ordering, inquiry predicate and indexes

An offer qualifies when this person sent a message tagged with that offer, in
its conversation, and this person is not the offer owner. Receiving a message or
replying as maker does not qualify. Match any qualifying sent message, not only
the first message in a pair's conversation. Enforce the conversation's participant
pair, including the offer owner, rather than relying on an arbitrary offer tag.

Illustrative SQL, with person bound from the authenticated session:

```sql
AND o.user_id <> $person
AND EXISTS (
    SELECT 1 FROM message m
    JOIN conversation c ON c.id = m.conversation_id
    WHERE m.sender_id = $person AND m.offer_id = o.id
      AND ((c.user_low = $person AND c.user_high = o.user_id)
        OR (c.user_high = $person AND c.user_low = o.user_id))
)
```

The EXISTS form above defines membership, not the final retrieval ordering.
Public uses `(o.created_at DESC, o.id DESC)`. Saved joins the unique own saved row
before LIMIT and uses `(saved_offer.created_at DESC, saved_offer.id DESC)`, matching
`/profile/saved` and its existing `idx_saved_offer_user_created` index. Public
facets and visibility still apply, so unavailable placeholders remain specific to
the profile collection.

The read-time candidate for Inquired first selects this sender's qualifying messages with the same participant
and non-owner checks, groups by offer, and computes `MAX(m.created_at)` as
`last_inquiry_at`. Join that one-row-per-offer relation to visible offers, apply
public facets, then order/page by `(last_inquiry_at DESC, o.id DESC)` before LIMIT.
Received replies never move an offer. Aggregation prevents repeated-message duplicates.
Cursor variants encode the scope's tuple and bind to normalized facets/scope;
reject cross-scope cursors rather than interpreting a timestamp with new semantics.

This deliberately pays for activity ordering: an old offer messaged yesterday
should be easy to retrieve. A new inquiry can move a row between pages; no snapshot
is promised. Do not silently fall back to offer-age order for performance.

Propose `(sender_id, offer_id, created_at DESC) WHERE offer_id IS NOT NULL` on
message for sender selection/grouping; it does not eliminate the final aggregate
sort. Compare EXPLAIN (ANALYZE, BUFFERS) for correlated EXISTS versus sender-first
aggregation on sparse and dense histories, selective and broad facets, and later
pages. Record join direction, rows scanned, loops, sort/spill and timing; no planner
behavior is assumed. The local TEMP-fixture experiment in
[V0.7_QUERY_PLANS.md](V0.7_QUERY_PLANS.md) found sparse EXISTS scanning all
120k offers; sender-first aggregation with the proposed index avoided that scan.
Dense activity ordering still processed 30k messages/10k offers at about 154 ms
in one observation. Full selective-facet/pagination and contract-load gates remain
unverified; the index alone is not a dense-history solution. Before building the inquired scope, spike the best read-time candidate on the
contract's dense history and 2-core baseline. If it misses the per-class budget,
use a maintained per-person/per-offer last-inquiry row, updated atomically when a
qualifying tagged message is sent, with an indexed keyset on
`(person_id, last_inquiry_at DESC, offer_id DESC)` and a backfill from existing
qualifying messages. Preserve the participant/non-owner checks in both designs.
Record the chosen design and measurements before implementing that scope. No
choice of aggregation versus summary storage is claimed from the single 154 ms
observation; no spike or persistent summary migration is part of step 2. Retain saved uniqueness on
`(user_id, offer_id)` and the existing save-time index.

Verified in `migrations/012_images.sql`: `offer.image_count` exists. The feed in
`crates/haven-db/src/offers/feed.rs` uses exactly `o.image_count >= 1` for public
visibility. Propose `(category, created_at DESC, id DESC) WHERE image_count >= 1`
for the public category feed. Keep the partial predicate identical to production
visibility if that changes; verify index use with actual query plans, not assumption.
Personal orderings need their own access paths, not this offer-age index alone.

### Inquired read-time decision (2026-10-28)

The optimized grouped-history candidate still missed the dense SQL spike:
21.7 completed queries/sec at 1,000 offered/sec, 97.8% skipped and every completed
query beyond 200ms. An indexed latest-message representative avoids aggregating
all history. The scalar latest-id lookup is restricted to the same sender,
offer and conversation; the outer query validates the non-owner and exact
participant pair. Conversation-pair uniqueness leaves one qualifying conversation
per person/offer; ordering remains latest qualifying sent-message time then offer id.

After VACUUM, the streaming candidate sustained 1,002 broad queries/sec and
994 empty-category queries/sec in separate 30-second, 1,000-arrival/sec SQL spikes,
with zero skipped requests and zero completed queries beyond the 200ms latency
limit. Initial connection time is excluded from pgbench's reported TPS. This is
query-design evidence, not the HTTP performance gate. Cold plans, buffers, fixture
sizes and raw output are in [the spike record](V0.7_INQUIRY_SPIKE.txt); the
[streaming query](V0.7_INQUIRY_STREAMING.sql) is reproducible against the named
isolated synthetic schema. Choose read-time retrieval with the two activity
indexes for now; verify sparse/dense, selective and later-page HTTP classes.
If that gate misses its budget, reconsider maintained summary rows. No summary
migration or new message-write behavior is needed for this candidate.

## URLs, cache policy, and SEO

Public facets are normalized category, title and price/currency parameters.
Serialize them in a stable order, omit defaults, and preserve them across paging.
Changing any criterion or scope resets the cursor. Public links reproduce public
criteria; a copied personal-view URL selects the recipient's own scope after
sign-in, never the sender's history. Label personal views “Your saved offers” and
“Offers you inquired about”; do not present their URLs as shareable collections.

Index only unfiltered `/offers` and first-page single-category landings, with
normalized canonicals omitting defaults/cursors. Search, price, combined facets,
invalid input, pagination and personal views get `noindex, follow` and **no canonical**.

Separate public-offer discovery deliverable (outside the v0.7 narrowing gate):
add `/sitemap.xml` (with sitemap index/chunks when required), advertised in
`robots.txt`, containing canonical `/offers/{slug}` URLs for every publicly
available offer under the exact feed visibility predicate. This is the explicit
discovery path for offers beyond page one; do not depend on crawler traversal of
noindexed cursor pages. Include no personal or facet URLs. Keep it updated after
create/delete/visibility changes; offer detail pages remain indexable with canonical
slug URLs. Acceptance must verify a deep-page offer appears, unavailable/deleted
offers disappear, and generated URLs resolve publicly. Tags have no v0.7 URLs.

Personal scopes always use private/no-store and require authentication. Do not
set no-store on the entire route. Guest public facets retain shared caching.
Current code also renders per-person saved indicators and authentication UI for
signed-in visitors, and already uses private/no-store for them. Preserve that
protection even without a personal predicate; making that HTML shared-cacheable
would leak personalization. Public-facet query results can be shared internally
without sharing personalized HTML. Test headers and ETag/304 behavior for each
response class.
For the same URL, send `Vary: Cookie` on guest and authenticated responses (and
`Authorization` if supported as an authentication input), preserving existing Vary
fields. Only guest public HTML may use shared Cache-Control; any authenticated
HTML and personal-scope response is `Cache-Control: private, no-store`. Authenticate
before conditional/304 handling; never reuse a guest ETag to authorize a personal 304.

## Composition across crate boundaries

Use `Scope = Public | Saved(UserId) | Inquired(UserId)` separately from a
`PublicCriteria` collection containing only title/price facets in step 2 (category implementation follows the final prelaunch names/control review). Resolve
the person identifier from authentication, never query input. Resolve scope before querying;
repository dispatch selects membership, order and cursor type. Return a typed
response classification: `Personal` always renders private/no-store; the shared
renderer accepts only a public query result plus guest context. Authenticated
public-scope HTML is private too because it contains personalized controls. No
conversion from personal results to the shared response path is exposed. Test
these boundaries as well as headers; a criteria enum alone cannot enforce caching.

Each criterion has corresponding modules in the appropriate layer: domain value/validation, web parse/control/chip/URL behavior,
and database bound predicate emission. SQL stays in haven-db; UI stays in
haven-web. A web module must not own raw SQL or database dependencies.

The feed shell composes title/price parsing, summaries and URL contributions,
using the existing control components. Typed active facets dispatch database
predicates and web summaries. Controls retain their existing assembly and markup. The repository composes their bound SQL predicates
with common visibility, cursor, ordering and limit rules. Adding a criterion
requires its typed domain field/variant and validation, database and web modules,
and entries in each layer’s composition assembly, plus its control wiring. Those registry edits are page-assembly wiring; existing
criteria and feed layout need no changes. Modularity is per layer, not a single
self-contained module per criterion. Scope stays outside these registries. Keep this a
small typed design for existing criteria, not a plugin framework for future ones.

## Acceptance table

| Case | Required result |
|---|---|
| Existing/create/edit | Test/seed rows backfill to Other; category required on create/edit and round-trips; invalid submission retains fields |
| Combined criteria | Every result satisfies public facets and selected personal scope; no duplicates |
| Person isolation | Session supplies person; other people's saves/messages never qualify; own-offer replies do not qualify |
| Repeated messages/saves | One result per offer; idempotent save/unsave behavior unchanged |
| Empty states | Show all categories in stable order; distinguish no public offers, “No offers here yet” for an empty category, no combined-facet matches, empty saved history, and empty inquiry history; retain criteria |
| Invalid criteria | Show useful validation, preserve valid input, noindex; unknown category is invalid, not silently unfiltered |
| Cursor | Filter changes drop cursor; malformed cursor restarts first page with notice; valid stale cursor remains a tuple boundary even if its row was deleted |
| Interrupted/back/refresh | Normalized criteria persist; pagination stays scoped; no snapshot consistency promised across edits |
| Deleted/unavailable/reclassified | Existing public visibility rules apply; unsaved offers leave Saved; no inaccessible details leak; `/profile/saved` placeholders unchanged |
| Privacy/cache/SEO | Guest/public and signed-in/personal classes follow the policy above, including 304 responses |
| Usability | Controls/chips work through SSR, keyboard and narrow-screen layouts; open/return preserves criteria |

Existing slugs freeze at launch; new categories may be added. Before launch,
renames/merges may use migrations after deliberate review. Cross-page changes may alter membership;
keyset pagination prevents duplicate rows from join multiplication, not a changing
collection from behaving like a frozen snapshot.
